# Бэкенд: приём оплаты и передача заявок в amoCRM

Проектный документ. Решения приняты 02.09.2026, стек согласован с владельцем после
трёх итераций — что именно отвергнуто и почему, записано в разделе «Стек».

Границы: бэкенд принимает заказы, выставляет счёт через Prodamus, отмечает оплату по
вебхуку и передаёт всё в amoCRM. Личного кабинета, выдачи уроков и админки в этом
этапе нет.

---

## Стек

| Слой | Выбор |
|---|---|
| HTTP | Fastify 5, плагинная изоляция модулей |
| Схемы, типы, OpenAPI | Zod 4 + `fastify-type-provider-zod` |
| БД | PostgreSQL 17 |
| Доступ к БД, миграции | Drizzle ORM + drizzle-kit |
| Очередь | pg-boss (очередь таблицами в Postgres) |
| Тесты | Vitest |
| Логи и алерты | pino → journald, уведомления в Telegram |
| Развёртывание | Docker Compose за Caddy, образы собирает GitHub Actions |

**Что отвергнуто и почему** — чтобы не возвращаться к этому на следующей итерации:

- **NestJS** — DI-контейнер и декораторы из Angular дают тройной объём кода на CRUD.
  Плагинная изоляция Fastify закрывает ту же задачу без контейнера.
- **SQLite** — однопоточная запись становится ограничением, как только появляется
  второй процесс, а он появляется сразу (воркер очереди).
- **Prisma** — движок запросов отдельным бинарником в каждом процессе (~60–80 МБ) и
  шаг `prisma generate` в каждой сборке. Схема на Drizzle — обычный TypeScript.
- **BullMQ + Redis** — третий демон ради десятков задач в день. Задачи BullMQ живут
  в Redis, а напоминание о доплате остатка ставится на недели вперёд: его потеря —
  это потерянные деньги. В Postgres оно лежит рядом с заказом и попадает в тот же
  бэкап.
- **Sentry на старте** — в стектрейсы платёжного бэкенда попадают телефон и почта
  покупателя; иностранный обработчик персональных данных на старте не нужен.
  Подключается позже, с настроенной вычисткой ПД.

Память на VPS 1 CPU / 2 ГБ: Postgres ~300 МБ, API с воркером ~180, Caddy ~20,
накладные Docker ~100 — около 600 МБ из 2048.

## Домен

### Заказ — это счёт, а не платёж

Ключевая особенность: **бронь за 10 000 ₽ — двухэтапная оплата.** По FAQ (слайд 8,
ответ 2) остаток довносится перед стартом обучения. Поэтому у заказа есть `total` и
`paid`, а не флаг «оплачен», и второй платёж — это второй `payment` по тому же
заказу.

```
Заказ (orders)  1 ──── N  Платёж (payments)
                              │
                              └── события от платёжки (payment_events)
```

### Статусы заказа

| Статус | Когда |
|---|---|
| `new` | создан, ссылка на оплату ещё не выдана |
| `awaiting_payment` | ссылка выдана, ждём вебхук |
| `partially_paid` | внесена бронь, остаток не внесён |
| `paid` | `paid_kopecks >= total_kopecks` |
| `cancelled` | отменён вручную |

Переход в `paid` и `partially_paid` делает **только обработчик вебхука**. Ни один
эндпоинт, доступный клиенту, статус оплаты не меняет.

### Три правила, нарушение которых означает переделку

1. **Сумму считает сервер.** Клиент присылает `{ tariffId, action }`, не рубли.
   Цены берутся из `packages/shared`, тот же источник, что у кнопок на странице.
2. **Вебхук идемпотентен.** Платёжки шлют дубли и ретраи. Порядок строго такой:
   проверили подпись → записали событие с уникальным ключом → ответили 200 → и
   только потом действуем. Повторное событие с тем же ключом не делает ничего.
3. **Карты у нас нет.** Prodamus отдаёт хостед-форму, реквизиты карты на наш сервер
   не попадают никогда. Это выводит проект из области PCI DSS, и ломать это нельзя
   никакой «формой оплаты прямо на сайте».

## Схема БД

Черновик прежней схемы поднимается из git: `git show 37c81ea:api/_lib/schema.ts`.
Ниже — что меняется относительно неё.

### `orders`

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | uuid pk | |
| `public_id` | varchar(16) unique | короткий номер для человека и для платёжки |
| `access_token` | varchar(64) | по нему страница «спасибо» спрашивает статус |
| `idempotency_key` | varchar(64) unique | двойной тап по кнопке не создаёт второй заказ |
| `tariff_id` | varchar(16) | `standard` / `premium` / `vip` |
| `action` | varchar(16) | `full` / `reserve` |
| `total_kopecks` | integer | полная стоимость тарифа |
| `paid_kopecks` | integer default 0 | сумма подтверждённых платежей |
| `status` | varchar(24) | см. таблицу статусов |
| `customer_phone` | varchar(32) | обязательно |
| `customer_email` | varchar(320) | обязательно |
| `customer_telegram` | varchar(100) | необязательно |
| `customer_whatsapp` | varchar(32) | необязательно |
| `utm` | jsonb | метки перехода, нужны маркетингу в CRM |
| `amo_contact_id` | bigint | заполняется после пуша в amoCRM |
| `amo_lead_id` | bigint | |
| `created_at` / `updated_at` | timestamptz | |

`total_kopecks` хранится даже при брони: это стоимость тарифа целиком, иначе остаток
не посчитать. Сумма первого платежа живёт в `payments`, а не в заказе.

### `payments`

`id`, `order_id`, `kind` (`initial` / `remainder`), `amount_kopecks`, `status`
(`pending` / `succeeded` / `failed`), `provider` (`prodamus`),
`provider_payment_id` unique, `payment_url`, `paid_at`, `created_at`.

### `payment_events`

`id`, `event_key` **unique**, `order_id`, `payment_id`, `signature_valid` boolean,
`payload` jsonb, `received_at`. Это и журнал для разбора, и механизм
идемпотентности: вставка с существующим `event_key` отбрасывается.

`signature_valid = false` тоже записывается — по этим строкам видно попытки подделки
и смену ключа.

### `consents`

Отдельная таблица, а не флаги в заказе: 152-ФЗ требует доказуемости, а доказуемость
это неизменяемая запись факта.

`id`, `order_id`, `kind` (`pd` — обработка персональных данных / `ads` — рекламная
рассылка), `text_version`, `accepted_at`, `ip`, `user_agent`.

Два согласия раздельные — ст. 18 закона «О рекламе» требует отдельного
предварительного согласия именно на рекламу (см. Q24 в `03-QUESTIONS.md`). Форма на
странице их уже разделяет.

pg-boss создаёт свою схему `pgboss` сам, руками её не трогаем.

## Эндпоинты

### `POST /api/orders`

```
{ tariffId, action, phone, email, telegram?, whatsapp?,
  consentPd: true, consentAds: boolean, idempotencyKey, utm? }
→ 201 { publicId, accessToken, paymentUrl }
```

Порядок: валидация Zod → расчёт суммы по `tariffId` и `action` → запись заказа,
согласий и задачи в CRM **одной транзакцией** → построение подписанной ссылки
Prodamus → ответ.

Повтор с тем же `idempotencyKey` возвращает **тот же** заказ и ту же ссылку.
Rate limit — `@fastify/rate-limit`.

### `GET /api/orders/:publicId`

С `accessToken`. Отдаёт статус и суммы для страницы «спасибо». Персональные данные
не возвращает.

### `POST /api/webhooks/prodamus`

Принимает уведомление о платеже. Тело нужно **сырым** — подпись считается до
разбора. Порядок из правила 2 выше. Отвечаем 200 быстро, работу с amoCRM отдаём в
очередь.

### `GET /api/health`

Проверка живости для внешней пинговалки. **Отдельно мониторить эндпоинт вебхука:**
если он лежит, оплаты проходят, а заказы не отмечаются, и узнаёшь ты об этом от
клиента.

## Prodamus

Схема работы: строим ссылку на платёжную форму с параметрами заказа и подписью
HMAC-SHA256 на секретном ключе магазина, отправляем человека туда, получаем вебхук.

⚠️ **Точные имена параметров, формат подписи и формат вебхука сверить с
документацией кабинета перед реализацией** — здесь описана схема, а не контракт.
Подпись и порядок полей у платёжек меняются между версиями, и угадывать их нельзя.

Что проверить в кабинете до написания кода:

1. **Штатная интеграция Prodamus с amoCRM.** Если она закрывает нужный сценарий,
   часть нашего кода не понадобится вовсе. Выяснить **до**, а не после.
2. **Как оформляется двухэтапная оплата** — отдельным товаром «бронь» или частичной
   оплатой заказа. От этого зависит, как выставляется счёт на остаток.
3. **Список IP, с которых приходит вебхук** — если он фиксированный, ограничиваем
   доступ на уровне Caddy.
4. **Чеки по 54-ФЗ** — Prodamus как платёжный агент обычно берёт это на себя;
   подтвердить и зафиксировать систему налогообложения продавца.

Секретный ключ живёт только в `.env` на сервере. Префикс `VITE_` для него запрещён —
уедет в бандл.

## amoCRM

**Авторизация — долгосрочный токен приватной интеграции.** OAuth с одноразовым
refresh-токеном не берём: любой сбой ротации кладёт интеграцию до ручного
перезахода.

**Заявка едет в CRM до оплаты.** Неоплаченный заказ — это лид, который нужен отделу
продаж; ждать вебхука, чтобы создать сделку, значит терять всех, кто не дошёл до
оплаты.

| Что | Куда |
|---|---|
| телефон, почта, telegram, whatsapp | контакт, стандартные поля |
| тариф, тип оплаты (полная или бронь) | пользовательские поля сделки |
| сумма | бюджет сделки |
| `public_id` заказа | пользовательское поле, для сверки |
| utm-метки | пользовательские поля |
| оплата подтверждена | смена статуса сделки |

`POST /api/v4/leads/complex` создаёт контакт и сделку одним вызовом. Лимит — около
7 запросов в секунду, при нашем объёме недостижим, но ретраи очереди должны его
уважать.

ID воронки и статусов — в конфиг, не в код: заказчик их поменяет.

## Очередь (pg-boss)

| Задача | Когда | Ретраи |
|---|---|---|
| `crm.push-order` | создание заказа | экспоненциальные, до суток |
| `crm.mark-paid` | подтверждённый платёж | так же |
| `notify.telegram` | новый заказ, оплата, ошибка подписи | 3 попытки |
| `payment.remind-remainder` | отложенно, перед стартом обучения | по расписанию |

Воркер сначала живёт **в процессе API**: все задачи — HTTP-вызовы, они I/O-bound и
событийный цикл не держат. Вынести в отдельный процесс — одна строка, делаем по
факту, а не заранее.

## Структура репозитория

Переезд на npm workspaces делается **до** написания серверного кода — потом он стоит
втрое дороже.

```
apps/
  web/        ← текущий Vite + React целиком
  api/        ← Fastify
    src/
      modules/   orders/  payments/  crm/
      jobs/
      plugins/   db.ts  queue.ts  telegram.ts
      db/        schema.ts  migrations/
packages/
  shared/     ← TariffId, PayAction, цены, контракты запросов
docker-compose.yml
```

`packages/shared` существует ради одного: **цена курса не должна существовать в двух
местах.** Рассинхрон цены на кнопке и цены в счёте — самая дорогая ошибка из
возможных. `src/data/tariffs.ts` для этого уже пригоден — он не импортирует ни
React, ни ассетов.

## Развёртывание

VPS 1 CPU / 2 ГБ, **обязательно в РФ** — 152-ФЗ, ст. 18.5: персональные данные
россиян хранятся в России.

Caddy: автоматический TLS, отдаёт `apps/web/dist` статикой мимо приложения,
проксирует `/api` в контейнер.

**На сервере ничего не собирается.** Образы собирает GitHub Actions и кладёт в GHCR,
VPS делает `docker compose pull && up -d`. `npm ci` и `vite build` на одном ядре —
это минуты и своп.

Postgres тюнится сразу, дефолтный конфиг рассчитан на другую машину:
`shared_buffers=256MB`, `effective_cache_size=768MB`, `max_connections=20`,
`work_mem=8MB`.

**Бэкапы:** `pg_dump` по расписанию в объектное хранилище в РФ. Бэкап, из которого ни
разу не разворачивались, бэкапом не является — восстановление проверить один раз
руками и записать сюда дату проверки.

Время в базе — **UTC**, показ — MSK.

## Чего не хватает от заказчика

Без первых четырёх пунктов приём оплаты включать нельзя — юридически, а не
технически (подробности в Q24 `03-QUESTIONS.md`):

1. **Реквизиты продавца** — ИП или ООО, ИНН, ОГРН/ОГРНИП, адрес, контакты.
   Сейчас `SELLER` в `src/data/legal.ts` пуст.
2. **Публичная оферта** и **политика обработки персональных данных** — тексты и
   ссылки. `LEGAL_DOCS` сейчас с пустыми `href`.
3. **Кабинет Prodamus** — URL платёжной формы и секретный ключ.
4. **amoCRM** — поддомен, долгосрочный токен, ID воронки и статусов.
5. Номер WhatsApp для трёх кнопок (Q18, висит с августа).
6. Домен и доступ к VPS.

## Порядок работ

1. ✅ Переезд на npm workspaces, `packages/shared` с ценами (коммит `c54df18`).
2. ✅ Каркас Fastify: конфиг с проверкой окружения, логи, `/health` с проверкой
   базы, подключение Drizzle, Docker Compose с Postgres и Caddy, обвязка миграций.
3. ✅ Схема БД (4 таблицы, миграция `0000_orders_payments_consents`) и
   `POST /api/orders` + `GET /api/orders/:publicId` без платёжки — заказ
   создаётся и лежит, `paymentUrl` в ответе пока `null`. Проверено на живом
   PostgreSQL 17: 26 тестов, включая гонку пяти одновременных запросов с одним
   ключом повтора.
4. Prodamus: подписанная ссылка, вебхук, идемпотентность. Тесты на подпись и на
   повторное событие — это места, где ошибка стоит денег.
5. Очередь и amoCRM.
6. Уведомления в Telegram, страница «спасибо», бэкапы, мониторинг.
7. Включение приёма оплаты — только после пунктов 1–4 из списка «Чего не хватает».
